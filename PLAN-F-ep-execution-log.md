### Held this cycle — STOP → CODEX-HELD

Per the ambiguity-ladder / Codex-review protocol ("Ambiguous fix... do NOT guess. Record unresolved and STOP the loop → CODEX-HELD"), the following findings were judged too architecturally deep, or genuinely ambiguous against the plan's stated scope, to fix confidently in an unattended pass. Each is logged below as `[FOLLOWUP]` and left for a human-supervised `/rp` or hand-authored fix:

- **[FOLLOWUP] callId-based bulk-outcome↔confirmation matching (found by all 3 lenses).** `stage6-event-bundler.js`'s bulk-outcome consumption currently matches a staged `bulkOutcomes` ledger entry to its confirmation by `(field, boardId, applied circuit set)`, ignoring the `callId`/`value` the ledger already carries. Two same-turn bulk calls to the same field+board with DISJOINT circuit targets (e.g. a range-restricted first call, then a second call covering different circuits) would have the second ledger entry's REPLACE semantics (fix #2 above) silently discard the first call's disclosure rather than amend two separate confirmations. This needs `callId` threaded through `synthesiseConfirmations()` as transient per-group metadata so each bulk call's outcome joins its own confirmation, not the nearest field/board match. Risk of a rushed fix: `stage6-event-bundler.js` is dense, high-traffic, shared code (PLAN-B's fast-correlation logic lives in the same function) — a wrong match-key change risks silently misattributing OTHER plans' confirmations, not just PLAN-F's.
- **[FOLLOWUP] Single/range scope + spare_policy composition (lens 2, `intent_verdict: null`, i.e. Codex judged it in-scope).** The current `indicesForScope`/`resolveCircuitScope` implementations carry a considered code comment: "single/range — an explicitly-named circuit is never spare-filtered, matching the backend (the spare filter only applies to the bulk 'all' candidate set)." The reviewer's finding assumes the plan's "the filter composes with ANY selector" (line 62) extends to the CLIENT-side single/range command shape, but that sentence's context is the BACKEND's `scope` tool-input enum (`all`/`non_spare`/`rcd_protected_only` — all bulk selectors); the plan's truth table (lines 65-74) enumerates only those three backend selector values, and the plan's title itself is "spares in bulk apply." Whether "circuits 3 to 5, excluding spares" (a range with a spare inside it) should silently apply to all 3 or filter+disclose is a genuine product decision the plan doesn't unambiguously settle — NOT a clear bug to guess-fix.
- **[FOLLOWUP] LIM capability gate runs before spare-filter candidate resolution (lens 3).** `dispatchSetFieldForAllCircuits` (`stage6-dispatchers-circuit.js`) checks the `lim_ranged_write_v1` capability gate BEFORE resolving the post-selector/post-spare-filter candidate set. On the narrow edge case of a board where every eligible circuit is a spare (so the real candidate set is empty regardless of capability), the inspector would hear "capability missing" instead of the correct "No non-spare circuits were updated" wording. Fix requires hoisting a side-effect-free candidate preflight above the capability check — a real restructure of a function that already handles coercion, clamping, numeric validation, and cross-board `'*'` fan-out in sequence; risk of reordering something load-bearing outweighs the narrow-edge-case value in an unattended pass.
- **[FOLLOWUP] Multi-board omitted-`board_id` ledger entries don't carry PLAN-A2's effective-board enrichment (lens 3).** For a bulk call with omitted `board_id`, `stageBulkOutcomeForBundler` stores `boardId: null` even though the dispatcher resolves a real current board; PLAN-A2 separately enriches confirmations with their effective board id. A turn that implicitly targets two different boards in sequence (via `select_board`) could have both ledger rows collapse to the same boardless key. This is the deepest of the held findings — it touches the effective-board-id resolution mechanism PLAN-A2 built specifically to prevent cross-board leaks, and a wrong fix here risks reintroducing the exact class of bug A2 closed.
- **[FOLLOWUP] No dedupe token for standalone/fallback bulk confirmations (lens 2).** The zero-applied and unmatched-fallback disclosure entries carry a non-null `field` but no operation token, so iOS/web's session-permanent field-confirmation dedupe store can swallow a genuine repeat (a second identical all-spares command in the same session, on the same field) as if it were a replay. Needs a replay-stable token (e.g. `bulkoutcome_<turn>_<call>`) threaded through the backend dedupe-key builder AND both clients' equivalents — a 3-repo wire-adjacent change best done with its own review cycle, not folded into an unattended fix pass.
- **[FOLLOWUP] No "real-ingress" regression for the contradiction-handling prompt guidance (found by all 3 lenses).** The existing `stage6-plan-f-spare-policy-prompt.test.js` is a static prompt-content test (asserts the prose survives future edits); the plan calls for proof that the PRODUCTION ingress path (`initSonnetStream`) never dispatches a mutator tool call on a contradictory utterance. Assessed but not added: there is no deterministic backend-side contradiction detector (contradiction handling is a MODEL-restraint concern per the prompt, not a dispatcher validation — see the existing test's own doc comment), so a "real-ingress" test would necessarily mock the model's tool-call response and mainly prove the harness's own plumbing rather than real model judgment. Left as a follow-up for a deliberate decision on what such a test should actually assert, rather than authoring one that gives false confidence.
